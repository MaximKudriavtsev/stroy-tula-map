# Общие инструкции для агента реализации

Цель: создать интерактивный портал строительства Тульской области с картой, административной панелью и обработкой сообщений через MAX.

Этот документ применяется вместе с 01-contracts.md и одним заданием Fxx. Набор готов для переноса в репозиторий как docs/agent-prompts/. Файлы описывают предлагаемую структуру нового проекта: существующий исходный код в этой задаче не предоставлен.

## Как выполнять задание

1. Прочитай AGENTS.md целевого репозитория, этот документ, 01-contracts.md и целиком выбранный файл features/Fxx-*.md.
2. Режим по умолчанию — MVP. V2 и TARGET реализуй только при явном выборе соответствующего режима. В V2 входят принятый MVP и указанное приращение; в TARGET — принятые предшествующие версии и целевые изменения.
3. Проверь входные зависимости. Разделяй готовность контракта, реализацию поставщика и проверенную интеграцию.
4. Если сервер соседней команды ещё не готов, используй общий API mock из packages/fixtures с теми же схемами. Не создавай параллельный production API или собственные несовместимые DTO.
5. Выполняй конкретное задание и проверки до работающего результата. Если нет внешнего доступа, заверши локальную часть, перечисли отсутствующие доступы и не называй внешнюю интеграцию проверенной.
6. Не перестраивай готовый репозиторий под этот документ. Если структура уже существует, составь таблицу соответствия путей и сохрани границы владения. Существенное изменение общего контракта сначала передай интегратору.
7. Ты работаешь одновременно с другими разработчиками и агентами. Не отменяй их изменения. Работай в своей ветке/worktree; интегратор объединяет изменения.
8. Не добавляй целевые возможности за счёт MVP. Не оставляй активные кнопки, которые лишь показывают фиктивный успех.
9. По завершении верни изменённые пути, команды и результаты проверок, примеры API/экранов, ограничения и зависимости следующего задания. Подготовь docs/handoffs/Fxx.md по шаблону 02-handoff.md.
10. Коммиты и отправка изменений выполняются в принятом командой процессе. Не публикуй код, сайт или сообщения реальным пользователям без соответствующего задания.

## Стек и единый репозиторий

Для нового проекта: TypeScript, pnpm workspace, React + Vite, NestJS, PostgreSQL + PostGIS, BullMQ + Redis, S3-совместимое хранилище, MapLibre GL JS + Three.js. F00 фиксирует совместимые версии и lockfile после проверки. Не выбирай другие major-версии в отдельных заданиях.

Предлагаемая структура:

```text
apps/
  public-web/src/{app,features}
  admin-web/src/{app,features}
  api/src/{app,platform,modules}
  worker/src/{app,jobs}
packages/
  contracts/src/{common,objects,media,timeline,metrics,workflow,bot,analysis,extras}
  api-client/src/generated
  db/src/{client,registry}
  db/migrations/Fxx/
  domain/src/{temporal,metrics,workflow,priority}
  map-runtime/src
  bot-core/src
  model-library/src
  fixtures/src/{objects,workflow,bot,metrics}
  ui/src
docs/{agent-prompts,handoffs,adr}
infra/
tests/{contracts,integration,e2e}
```

F00 владеет корневыми package.json, pnpm-lock.yaml, tsconfig, общими lint/test настройками, OpenAPI, генератором клиента и начальными точками запуска приложений.
После F00 назначенный интегратор владеет изменениями общих контрактов и регистрацией новых модулей/маршрутов. Локальный агент экспортирует модуль и описывает подключение в handoff. Реестр миграций упорядочивает интегратор; каждый исполнитель добавляет миграции только в папку своей фичи. Уже применённые миграции не переписываются.
В worktree исполнитель может подключить свой модуль для сквозной проверки, но оформляет это отдельным изменением для интегратора.

F05 владеет packages/map-runtime и корневой композицией карты. Остальные карты и 3D-фичи подключаются через его интерфейс.
F06 владеет композицией редактора объектов; дополнительные панели экспортируются отдельными модулями.
F13 владеет композицией экрана обработки обращений.
Запрос новой зависимости включает пакет, назначение, совместимость и место использования. Добавление в общий lockfile координирует интегратор.

## Неизменяемые правила предметной области

- 95 проектов — сведения из описания; сами Excel/CSV пока не проверены. Не генерируй 95 якобы реальных записей.
- CSV и Excel могут быть копиями одного реестра. Повторный импорт не удваивает данные.
- Проект и физическое сооружение — разные сущности. Проект может содержать несколько объектов.
- Нет координат — объект виден в списке, но без выдуманной точки.
- Нет подтверждённого статуса — UNKNOWN. Нет числа — null. Ноль означает измеренное нулевое значение.
- План, факт и текущие сведения без исторической даты различаются.
- Демонстрационные записи dataOrigin=DEMO. По умолчанию они исключены из реальных публичных агрегатов.
- F00 вводит DATA_MODE=real|demo. В demo frontend явно отправляет dataOrigin=DEMO и показывает общий баннер; в real начальный запрос dataOrigin=REAL. Demo fixtures не подмешиваются к real ответу при пустой выдаче.
- Условная модель реального объекта не делает сам объект демонстрационным. Качество модели хранится отдельно и отображается в карточке.
- Обращение и задача — разные сущности. Несколько обращений могут быть связаны с задачей, каждое сохраняет свой номер и ответ.
- LLM даёт рекомендации. Решения об отказе, объединении, ответе и закрытии принимает уполномоченный сотрудник.
- Сбой LLM не влияет на надёжную регистрацию обращения.
- Собственный номер обращения не выдаётся за номер ПОС или иной государственной системы.

## Проверки и завершение

F00 создаёт выполняемые корневые команды:
- pnpm install --frozen-lockfile — установка зафиксированных зависимостей.
- pnpm lint — статическая проверка.
- pnpm typecheck — типы всех workspace-пакетов.
- pnpm test:unit -- --feature=Fxx — meaningful unit tests фичи; тестовый runner должен действительно поддерживать этот фильтр.
- pnpm test:integration -- --feature=Fxx — интеграционные проверки с отдельной тестовой БД и адаптерами.
- pnpm test:e2e -- --feature=Fxx — браузерные сценарии по тегу фичи.
- pnpm contracts:check — соответствие API, схем и клиента.
- pnpm build — сборка.
- pnpm dev — локальный запуск приложений после готовности зависимостей.
- pnpm db:migrate и pnpm seed:demo — миграции и идемпотентный seed только для development/demo.

Эти команды — требование к F00, а не утверждение, что они уже существуют. Успех проверки — exit code 0 и выполнение ожидаемых сценариев. Пустая выборка тестов не считается успешной проверкой.
Сначала зафиксируй тест для бизнес-правила, воспроизведи ожидаемый сбой, реализуй поведение и проверь повторно. Для визуальной вёрстки используй браузерные сценарии и ручной просмотр; не пиши тесты, повторяющие JSX.
Не заявляй прохождение команды, которую не запускал. Недоступные внешние проверки перечисляй отдельно.
