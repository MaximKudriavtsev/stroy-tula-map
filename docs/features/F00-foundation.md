# F00. Каркас репозитория и заморозка контрактов

**Цель:** Команда получает один согласованный контракт и запускаемый каркас. Все последующие задания могут компилироваться против реальных schemas и fixtures.
**Архитектура:** модуль существующего монорепозитория по contracts v1; разделённые production adapters и fixtures.
**Стек:** общий стек из 00-common.md; новые зависимости согласуются с интегратором.
**Приоритет:** Обязательный старт
**Исполнитель:** Интегратор / backend

## Готовый промпт для агента

Ты реализуешь фичу F00 «Каркас репозитория и заморозка контрактов» портала строительства Тульской области.
Прочитай docs/agent-prompts/00-common.md, docs/agent-prompts/01-contracts.md и этот файл полностью. Если пакет приложен отдельно, используй эти документы из его корня. Не проси пользователя повторять сведения из них.
Режим по умолчанию — MVP. Выполни его до проверяемого результата. Если пользователь явно выбрал V2 или TARGET, сначала проверь принятую предыдущую реализацию и выполни только соответствующее приращение. Не переписывай готовый MVP.
Ты не один в репозитории: сохраняй чужие изменения, соблюдай границы файлов. Общие DTO, корневые конфиги и lockfile изменяет интегратор. Внешний доступ не подменяй фиктивным успешным ответом.

## MVP — реализовать сейчас

1. Проверить репозиторий и локальные инструкции. Для нового проекта создать pnpm workspace по 00-common.md; для существующего зафиксировать соответствие путей. Выбрать совместимые стабильные версии, установить их и зафиксировать lockfile.
2. Реализовать runtime-схемы типов из 01-contracts.md. Для каждого объявленного endpoint задать точные request/response/error schemas, pagination и permissions. Сгенерировать типизированный клиент. Не подменять неизвестные бизнес-поля any.
3. Создать fixtures: условная школа, медицинское учреждение, котельная, объект без координат, неизвестный статус, несколько событий FACT/PLAN, два разных заявителя одной проблемы. Все записи DEMO; названия «Демонстрационная школа А» без выдачи за реальные адреса.
4. Сделать API mock на тех же схемах для двух frontend-приложений и MessengerAdapter simulator. Дать единый переключатель API_MODE=mock|live; production сборка не включает dev routes и открытые fixture endpoints.
5. Запустить API /health/live и /health/ready; readiness проверяет доступность обязательных хранилищ. Создать DB client, registry миграций и рабочие контейнеры PostGIS, Redis, S3-compatible storage; без бизнес-таблиц соседних фич.
6. Создать исполняемые команды из 00-common.md. Feature test runner принимает --feature=Fxx и завершается ошибкой, если сценарии для заявленной проверки отсутствуют. Создать минимальные contract tests на схемы и ошибки.
7. Подготовить базовый UI: router, layout, загрузка/ошибка/пусто, формы и таблица, общие design tokens. Язык интерфейса русский; карты пока подключаются через слот.
8. В ADR зафиксировать владельца общих файлов, каталог миграций, порядок регистрации модулей и версию контракта. Принять F00 только после запуска обеих веб-страниц и round-trip fixture через mock и валидатор.

## Проверяемые сценарии MVP

1. Чистый checkout + install frozen + build → обе веб-сборки и API собираются.
2. Невалидные UUID, даты, координаты и enum → schema error; valid fixtures → pass.
3. Ответ mock и generated client соответствуют одному OpenAPI.
4. Запуск тестов с неизвестной фичей не даёт ложного зелёного результата.
5. production config запрещает simulator и запуск seed:demo.

Для бизнес-логики сначала реализуй перечисленные сценарии как падающие тесты, проверь ожидаемую причину падения, затем добавь реализацию. Для UI проверь действия через браузер и сохрани доказательство поведения. Контракт API проверяется общими schemas.


## TARGET — отдельное задание после приёмки MVP

Исполнять только если выбран режим TARGET. Сначала сохранить совместимость и данные принятой предыдущей версии.

1. Добавить CI с проверкой схем, совместимости OpenAPI и generated diff. Несовместимый контракт блокирует merge.
2. Разделить demo/staging/production конфигурации; подключить secret store окружения, dependency scanning и воспроизводимые deploy artifacts.
3. Реализовать проверку запуска миграций на чистой БД и последовательное обновление с предыдущей версии.

Приёмка TARGET: перечисленные целевые поведения работают на согласованных данных и доступах, сценарии предыдущих версий проходят, миграции проверены на непустой БД. Если внешний источник недоступен, локальный adapter может быть готов, а внешняя приёмка остаётся открытой.

## Проверки и передача

Запусти после реализации соответствующие изменениям команды из 00-common.md:
```bash
pnpm typecheck
pnpm contracts:check
pnpm test:unit -- --feature=F00
pnpm test:integration -- --feature=F00
pnpm test:e2e -- --feature=F00
pnpm build
```
Не запускай неподходящую категорию как формальность: в handoff объясни, какие из unit/integration/e2e применимы этой фиче и какие реально выполнены. При применимом тестовом наборе ноль сценариев — ошибка проверки.
Подготовь docs/handoffs/F00.md по 02-handoff.md: изменённые файлы, exports, точное подключение, env, миграции, проверки, известные ограничения и интеграционный сценарий.
