# F01. Вход сотрудников, права и аудит

**Цель:** Любой защищённый модуль получает одну политику доступа; браузер не может обойти ограничения прямым запросом.
**Архитектура:** модуль существующего монорепозитория по contracts v1; разделённые production adapters и fixtures.
**Стек:** общий стек из 00-common.md; новые зависимости согласуются с интегратором.
**Приоритет:** P0
**Исполнитель:** Backend / безопасность доступа

## MVP — реализовать сейчас

1. Создать users, roles, municipality scopes, sessions и audit_log. Пароль хранить через поддерживаемый password-hashing алгоритм; не фиксировать известный production пароль в seed.
2. Реализовать POST login/logout и GET me. Cookie HttpOnly, Secure в production, SameSite=Lax; ограничить попытки входа, проверять CSRF для изменяющих запросов с cookie.
3. Составить явную action matrix: objects.read/write/publish/archive, imports.write, appeals.read/reply/link, tasks.read/update/transition/merge, assets.read/write, analysis.review, integrations.read/retry. Незнакомое действие deny.
4. ADMIN разрешён в назначенной административной области; OBJECT_EDITOR работает с объектами своей области; APPEAL_OPERATOR — с обращениями/задачами своей области; EXECUTOR — только назначенные задачи и необходимые вложения, без контактов заявителей.
5. Политика муниципалитета проверяется в SQL-выборке списков и повторно на detail/mutation. Для municipalityId=null доступ к изменению только ADMIN или явно назначенный оператор обработки неопределённой территории.
6. Сделать audit writer, который принимает actor, action, resource, before/after разрешённых полей и reason и пишет вместе с бизнес-изменением. Не логировать пароли, токены, full bot payload и приватные вложения.
7. Добавить страницу входа, возврат к запрошенному экрану после login, обработку 401/403 и истёкшей сессии. UI скрывает запрещённые действия, API остаётся источником решения.

## Проверяемые сценарии MVP

1. Прямой запрос EXECUTOR к чужой задаче → 403/404 по принятой политике и отсутствие данных.
2. Оператор одного муниципалитета не видит другой через list, detail, export или asset URL.
3. Успешная mutation содержит audit; rollback mutation не оставляет запись о состоявшемся изменении.
4. Logout инвалидирует сессию; повтор cookie не авторизует; без CSRF изменение отклонено.

Для бизнес-логики сначала реализуй перечисленные сценарии как падающие тесты, проверь ожидаемую причину падения, затем добавь реализацию. Для UI проверь действия через браузер и сохрани доказательство поведения. Контракт API проверяется общими schemas.


## TARGET — отдельное задание после приёмки MVP

Исполнять только если выбран режим TARGET. Сначала сохранить совместимость и данные принятой предыдущей версии.

1. Подключить корпоративный OIDC через отдельный adapter, связать внешние группы с локальными ролями и scope.
2. Добавить отзыв всех сессий пользователя, делегирование на срок и просмотр журнала с маскированием чувствительных полей.
3. Зафиксировать retention аудита и журнал административных изменений доступа, проверить нагрузку на фильтры доступа.

Приёмка TARGET: перечисленные целевые поведения работают на согласованных данных и доступах, сценарии предыдущих версий проходят, миграции проверены на непустой БД. Если внешний источник недоступен, локальный adapter может быть готов, а внешняя приёмка остаётся открытой.
