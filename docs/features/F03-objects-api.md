# F03. Реестр проектов, объекты и публикация

**Цель:** Опубликованные данные консистентны; импорт и редактор используют один Objects service.
**Архитектура:** модуль существующего монорепозитория по contracts v1; разделённые production adapters и fixtures.
**Стек:** общий стек из 00-common.md; новые зависимости согласуются с интегратором.
**Приоритет:** P0
**Исполнитель:** Backend объектов

## Готовый промпт для агента

Ты реализуешь фичу F03 «Реестр проектов, объекты и публикация» портала строительства Тульской области.
Прочитай docs/agent-prompts/00-common.md, docs/agent-prompts/01-contracts.md и этот файл полностью. Если пакет приложен отдельно, используй эти документы из его корня. Не проси пользователя повторять сведения из них.

Ты не один в репозитории: сохраняй чужие изменения, соблюдай границы файлов. Общие DTO, корневые конфиги и lockfile изменяет интегратор. Внешний доступ не подменяй фиктивным успешным ответом.

## MVP — реализовать сейчас

1. Создать проекты, физические объекты, редакции, организации/текстовые реквизиты и геометрии PostGIS. Один проект может содержать несколько объектов; импорт 95 строк не обязан создавать ровно 95 зданий.
2. Реализовать create/read/update draft с runtime-валидацией полей, If-Match, обязательными name/type/project/dataOrigin/source и nullable сведениями.
3. Реализовать атомарную публикацию: проверить все ссылки и геометрии, закрепить опубликованную редакцию, записать audit. Новые правки создают следующий draft, публичные запросы читают только publishedRevisionId.
4. Включить hooks опубликованных дочерних данных: media, events, metrics и model. До готовности расширений возвращать пустой проверенный набор; после подключения публикация фиксирует целую редакцию.
5. Сделать фильтры type/status/municipality/q, paging и GeoJSON map. В списке сохранять объекты без координат; в FeatureCollection таких точек нет. Не строить автоматически contour по generic 3D.
6. Поддержать geometry Point/Polygon/LineString и необходимые Multi-типы; проверять valid geometry, диапазоны и подтверждение редактором. Representative anchor для линии/полигона явно вычисляется, не выдаётся за точку входа.
7. Архивирование снимает с текущей публичной выдачи и сохраняет историю и ссылки обращений. Существующее обращение не теряется после снятия объекта с публикации.
8. Поддержать идемпотентность create с внешним ключом импорта. Не принимать current status из будущей плановой даты.

## Проверяемые сценарии MVP

1. Публикация R1 → редактирование R2: публичная карточка и media всё ещё R1 до publish.
2. Два PATCH с одной version: только один принят, другой 409.
3. Объект без координат есть в list и отсутствует в map features.
4. Архивирование объекта не удаляет обращения и audit.
5. Фильтры и totals применяются одинаково к map/list, за исключением отсутствующих геометрий.

Для бизнес-логики сначала реализуй перечисленные сценарии как падающие тесты, проверь ожидаемую причину падения, затем добавь реализацию. Для UI проверь действия через браузер и сохрани доказательство поведения. Контракт API проверяется общими schemas.


## TARGET — отдельное задание после приёмки MVP

Исполнять только если выбран режим TARGET. Сначала сохранить совместимость и данные принятой предыдущей версии.

1. Добавить workflow согласования редакции: редактор подаёт, уполномоченный публикует; показать diff полей и геометрий.
2. Добавить пространственный поиск по bbox и индексы после измерения нагрузки; full-text и aliases для поиска.
3. Поддержать набор сооружений проекта, связи реконструкции/замены и экспорт опубликованного реестра с источниками.

Приёмка TARGET: перечисленные целевые поведения работают на согласованных данных и доступах, сценарии предыдущих версий проходят, миграции проверены на непустой БД. Если внешний источник недоступен, локальный adapter может быть готов, а внешняя приёмка остаётся открытой.

## Проверки и передача

Запусти после реализации соответствующие изменениям команды из 00-common.md:
```bash
pnpm typecheck
pnpm contracts:check
pnpm test:unit -- --feature=F03
pnpm test:integration -- --feature=F03
pnpm test:e2e -- --feature=F03
pnpm build
```
Не запускай неподходящую категорию как формальность: в handoff объясни, какие из unit/integration/e2e применимы этой фиче и какие реально выполнены. При применимом тестовом наборе ноль сценариев — ошибка проверки.
Подготовь docs/handoffs/F03.md по 02-handoff.md: изменённые файлы, exports, точное подключение, env, миграции, проверки, известные ограничения и интеграционный сценарий.
**Критерий завершения:** Опубликованные данные консистентны; импорт и редактор используют один Objects service.
