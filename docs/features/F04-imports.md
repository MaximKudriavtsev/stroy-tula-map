**Цель:** Редактор может загрузить реестр, исправить ошибки и применить изменения без дублей и выдуманных сведений.

**Исполнитель:** Данные / backend

## MVP — реализовать сейчас

1. Если исходные файлы доступны, составить профиль колонок и отчёт качества. Если нет — подготовить маленькие DEMO CSV/XLSX с теми же типами полей и явно указать, что реальная схема ещё не проверена.
2. Реализовать загрузку в staging, выбор листа XLSX и mapping колонок. Ограничить строки/размер; формулы и макросы не исполнять, формульные значения не считать подтверждёнными без правила импорта.
3. Нормализовать пробелы, варианты названий/статусов, даты и единицы через версионированные словари. Сохранять raw value и source row; неизвестные единицы отправлять на исправление.
4. Сначала сопоставлять source system + externalId. При его отсутствии хранить решение оператора по source record mapping; похожее название/адрес только кандидат на дубль, не основание автоматического слияния.
5. Показать preview: create/update/unchanged/conflict/error, количество строк и отличия полей. Ошибки содержат строку, колонку, исходное значение и конкретное исправление.
6. Commit принимает выбранные проверенные строки и mapping version. Зафиксировать результат построчно; повтор commit не повторяет create. Изменять drafts, без автоматической публичной публикации.
7. Для двух форматов одного реестра повтор загрузки должен показать unchanged или сопоставленные updates. Не складывать количества проектов CSV и XLSX.
8. Добавить очередь качества: нет координат, неизвестный статус, нет источника/даты, спорный дубль. Не проставлять координаты центра муниципалитета вместо адреса.

## Проверяемые сценарии MVP

1. Один DEMO реестр CSV + XLSX → одно множество externalId, без удвоения.
2. Две разные стройки с похожими названиями → конфликт для человека, не merge.
3. Повтор commit после сетевого обрыва → те же результаты и ID.
4. Дата неоднозначна или мощность с неизвестной единицей → конкретная ошибка, не придуманные значения.
5. Ошибочные строки не публикуются и не повреждают успешные drafts.

Для бизнес-логики сначала реализуй перечисленные сценарии как падающие тесты, проверь ожидаемую причину падения, затем добавь реализацию. Для UI проверь действия через браузер и сохрани доказательство поведения. Контракт API проверяется общими schemas.


## TARGET — отдельное задание после приёмки MVP

Исполнять только если выбран режим TARGET. Сначала сохранить совместимость и данные принятой предыдущей версии.

1. Добавить сохранённые mapping profiles, инкрементальные импорты, dry-run diff и возобновление больших batch.
2. Добавить геокодирование через отдельно разрешённого провайдера: source/confidence и обязательное подтверждение неоднозначных результатов.
3. Добавить отчёт изменений источника и конфликты «редактор изменил вручную после прошлого импорта»; ручные изменения не затираются молча.

Приёмка TARGET: перечисленные целевые поведения работают на согласованных данных и доступах, сценарии предыдущих версий проходят, миграции проверены на непустой БД. Если внешний источник недоступен, локальный adapter может быть готов, а внешняя приёмка остаётся открытой.
