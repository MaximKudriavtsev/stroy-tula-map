# F07. 3D: типовые сооружения → GLB → реальные модели

**Цель:** MVP показывает разные узнаваемые типы сооружений без зависимости от производства реальных 3D-ассетов. Целевая точность подключается тем же интерфейсом.
**Архитектура:** модуль существующего монорепозитория по contracts v1; разделённые production adapters и fixtures.
**Стек:** общий стек из 00-common.md; новые зависимости согласуются с интегратором.
**Приоритет:** P1, рекомендуемая ранняя демонстрация
**Исполнитель:** 3D / frontend

## Готовый промпт для агента

Ты реализуешь фичу F07 «3D: типовые сооружения → GLB → реальные модели» портала строительства Тульской области.
Прочитай docs/agent-prompts/00-common.md, docs/agent-prompts/01-contracts.md и этот файл полностью. Если пакет приложен отдельно, используй эти документы из его корня. Не проси пользователя повторять сведения из них.
Режим по умолчанию — MVP. Выполни его до проверяемого результата. Если пользователь явно выбрал V2 или TARGET, сначала проверь принятую предыдущую реализацию и выполни только соответствующее приращение. Не переписывай готовый MVP.
Ты не один в репозитории: сохраняй чужие изменения, соблюдай границы файлов. Общие DTO, корневые конфиги и lockfile изменяет интегратор. Внешний доступ не подменяй фиктивным успешным ответом.

## Вход и зависимости

F00 contracts; MapRuntime F05. MVP не требует реальных моделей и внешнего model API.

**Условие интеграции:** MVP можно готовить одновременно с F05 в отдельной scene; интегрировать после runtime. V2/TARGET требуют F02 и панель F06.

**Потребляет:** GenericModelFactory, ModelDescriptor, MapExtension; object type/status/anchor; MediaRef для V2.

**Предоставляет:** Процедурные модели типов, один совместимый map 3D layer, fallback, модельная панель; реестр GENERIC/ADAPTED/VERIFIED.

## MVP — реализовать сейчас

1. Реализовать GenericModelFactory.create({type,stage,quality}) из простых геометрий Three.js. SCHOOL — несколько низких корпусов; KINDERGARTEN — 2–3 небольших блока; MEDICAL — корпус с пристройкой; SPORT — зал с арочной/плоской крышей; CULTURE — зал со входной частью.
2. Дополнить HOUSING этажным блоком, BOILER корпусом с трубой, WATER резервуаром/насосной, WASTEWATER ёмкостями и служебным блоком, OTHER нейтральным объёмом. LINEAR отображать трассой, без фиктивного здания. Не искать и не генерировать реальные адресные модели для MVP.
3. Задать единые единицы в метрах, origin по земле, оси и deterministic seed. Типовые размеры — параметры иллюстрации; quality=GENERIC и dimensionsVerified=false. В UI постоянно доступна подпись «Условная модель по типу объекта; размеры и внешний вид не подтверждены».
4. Сделать состояния PLANNED: контур/полупрозрачный объём; IN_PROGRESS: условный каркас; COMMISSIONED: целый типовой объём; SUSPENDED: каркас с отличительным маркером; UNKNOWN: нейтральное представление. Эти виды обозначают статус, не точную степень завершённости.
5. Не генерировать фундамент или этажность на конкретную дату из процента готовности. Для шкалы брать stage только из TemporalState; до F08 использовать подтверждённый текущий статус.
6. Подключить MapExtension с Mercator transform, одним renderer/shared GL context согласно выбранной версии MapLibre. Полёт выполняет F05. Не создавать собственную интерактивную камеру, конфликтующую с картой.
7. Ограничить одновременно показываемые модели первичным бюджетом 30 generic и 1 selected detailed, применять instancing/shared materials где уместно. Снимать неиспользуемые scene nodes и освобождать geometry/material/texture с учётом shared references.
8. Облегчённый режим использует маркеры/контуры. Добавить standalone gallery всех типов и состояний для проверки без живой карты.

## Проверяемые сценарии MVP

1. Каждый ObjectType возвращает валидную сцену либо документированное LINEAR представление, все transform finite.
2. Одинаковый input даёт одинаковую модель; dimensionsVerified остаётся false для generic.
3. Выбор и смена статуса 50 раз не увеличивают без ограничения scene children и число retained resources.
4. Модель на тестовой точке совпадает с marker при zoom/pitch/bearing; screenshot на desktop/mobile.
5. Недоступный WebGL или выключенный 3D оставляет карту/список работоспособными.

Для бизнес-логики сначала реализуй перечисленные сценарии как падающие тесты, проверь ожидаемую причину падения, затем добавь реализацию. Для UI проверь действия через браузер и сохрани доказательство поведения. Контракт API проверяется общими schemas.

## V2 — отдельное задание после приёмки MVP

Исполнять только если выбран режим V2. Вход — принятый MVP этой фичи; внешние зависимости перечислены в шагах.

1. Добавить curated GLB каталог по типам с известным происхождением и лицензией. Это всё ещё GENERIC, если модель не адаптирована к конкретному объекту.
2. Загрузчик принимает только READY assets, задаёт timeout и fallback на procedural model. Начальный бюджет: GLB ≤5 MiB, ≤80 тыс. треугольников, текстуры ≤2048px; превышение показывает предупреждение редактору и остаётся на generic до оптимизации.
3. Сделать ModelDescriptor с отдельным preview, rotation/scale/altitude и revision binding. После save сохраняется draft; после publish модель доступна публично.
4. Приобрести/создать базовые GLB можно отдельно; при отсутствии файлов завершить loader и тесты на собственном минимальном fixture, честно указать незаполненный каталог.

Приёмка V2: все сценарии MVP проходят; для каждого нового поведения добавлена проверка успешного пути и указанного отказа.

## TARGET — отдельное задание после приёмки V2

Исполнять только если выбран режим TARGET. Сначала сохранить совместимость и данные принятой предыдущей версии.

1. Для трёх выбранных реальных объектов принять фотографии/чертежи или готовые модели от владельца. Без исходников не помечать модель VERIFIED и не объявлять достигнутой узнаваемость.
2. Поддержать ADAPTED: ручная подгонка типового корпуса к подтверждённому контуру; VERIFIED: проверенный объектом контент с источником, версией и датой согласования.
3. Добавить несколько LOD, worker-оптимизацию, texture compression, масштаб по подтверждённым размерам и контроль геопривязки. Каждый этап строительства требует отдельного подтверждённого asset/event mapping.
4. Добавить сопоставление фото и модели в редакторе и критерий принятия контента владельцем: внешний вид, посадка, высота, подпись источника. Проверить бюджет на целевых устройствах.

Приёмка TARGET: перечисленные целевые поведения работают на согласованных данных и доступах, сценарии предыдущих версий проходят, миграции проверены на непустой БД. Если внешний источник недоступен, локальный adapter может быть готов, а внешняя приёмка остаётся открытой.
