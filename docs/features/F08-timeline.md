# F08. Датированные события и временная шкала

**Цель:** Историческое представление объяснимо источниками и не создаёт отсутствующие этапы.
**Архитектура:** модуль существующего монорепозитория по contracts v1; разделённые production adapters и fixtures.
**Стек:** общий стек из 00-common.md; новые зависимости согласуются с интегратором.
**Приоритет:** P1
**Исполнитель:** Backend + frontend аналитики

## Вход и зависимости

F00; F03 для редакций, F05 runtime; F07 потребляет результат, но не блокирует разработку.

**Условие интеграции:** Resolver принимается раньше UI playback и подключения состояний 3D.

**Потребляет:** ObjectEvent, TemporalState, resolveObjectState; опубликованные event snapshots, URL at.

**Предоставляет:** Чистый resolver; timeline/events API; редактор событий и шкала; одинаковый state для карты, карточки и моделей.

## MVP — реализовать сейчас

1. Реализовать resolveObjectState(events,at) с фильтрацией FACT, published и supersession. Выбирать последнее подтверждённо наступившее событие. До первого факта UNKNOWN; PLAN не повышает статус.
2. Поддержать precision DAY/MONTH/YEAR через DateRange. При попадании at внутрь неопределённого диапазона показывать uncertain и предыдущий подтверждённый статус; не присваивать событию первое января автоматически.
3. Опубликовать GET events/timeline и включить at в F03 public map/list через единый resolver. Отдельно вернуть плановые события для иной визуальной дорожки.
4. Сделать редактор: дата/диапазон, статус, факт/план, progress с источником, документ, supersedes. Конфликт одинаковых дат требует явного разрешения до публикации.
5. Добавить шкалу с ручным выбором дня/месяца и play/pause. Во время playback подгружать компактную опубликованную историю один раз, либо кэшировать API по датам; не делать запрос каждый animation frame.
6. Все виджеты получают один выбранный at. Плановые итоги отдельно от фактических. Количество введённых считать по уникальным физическим объектам; число проектов показывать отдельно.
7. Выход из исторического режима возвращает текущий срез; браузер back восстанавливает at. UNKNOWN отображается как неизвестное, без анимированного строительства.

## Проверяемые сценарии MVP

1. Плановый ввод в 2025 без FACT на 2026 → не COMMISSIONED.
2. Первый факт 2024-05-10, at=2023-12-31 → UNKNOWN.
3. Дата ввода задана годом 2025, at=2025-06-01 → uncertain, без подтверждённого ввода.
4. Исправленное superseded событие исключено; конфликт дат блокирует publish.
5. Карта, карточка и 3D stage совпадают на одной дате.

Для бизнес-логики сначала реализуй перечисленные сценарии как падающие тесты, проверь ожидаемую причину падения, затем добавь реализацию. Для UI проверь действия через браузер и сохрани доказательство поведения. Контракт API проверяется общими schemas.

## V2 — отдельное задание после приёмки MVP

Исполнять только если выбран режим V2. Вход — принятый MVP этой фичи; внешние зависимости перечислены в шагах.

1. Добавить интервал from/to, предзагрузку исторических состояний и playback speed; reduced motion сохраняет пошаговое обновление.
2. Разделить количество введённых за период и накопленное количество к дате. Выбытие/снос учитывается отдельным типом события после расширения контракта.
3. Добавить историю исправлений без потери источников; экспорт событий объекта.

Приёмка V2: все сценарии MVP проходят; для каждого нового поведения добавлена проверка успешного пути и указанного отказа.

## TARGET — отдельное задание после приёмки V2

Исполнять только если выбран режим TARGET. Сначала сохранить совместимость и данные принятой предыдущей версии.

1. Поддержать valid time и recorded time для ответа «что было известно на дату отчёта»; миграция не переписывает старые факты.
2. Версионировать административные границы и привязку объекта, если нужен исторический муниципальный отчёт.
3. Материализовать большие срезы по измеренной нагрузке; проверять равенство с чистым resolver на контрольных случаях.

Приёмка TARGET: перечисленные целевые поведения работают на согласованных данных и доступах, сценарии предыдущих версий проходят, миграции проверены на непустой БД. Если внешний источник недоступен, локальный adapter может быть готов, а внешняя приёмка остаётся открытой.

## Опорный тест для реализации

Файл tests/unit/F08-temporal.spec.ts. Реализация экспортируется из packages/domain/src/temporal/index.ts. Это готовый начальный тест; остальные сценарии выше добавь отдельно.

```ts
import { expect, it } from 'vitest';
import { resolveObjectState } from '../../packages/domain/src/temporal/index';

it('F08: наступившая плановая дата не подтверждает ввод', () => {
  const state = resolveObjectState([{
    id: '00000000-0000-4000-8000-000000000001',
    objectId: '00000000-0000-4000-8000-000000000002',
    revisionId: '00000000-0000-4000-8000-000000000003',
    kind: 'PLAN',
    effectiveDate: { lower: '2025-01-01', upper: '2025-01-01', precision: 'DAY' },
    recordedAt: '2024-12-01T10:00:00Z',
    status: 'COMMISSIONED',
    progressPercent: null,
    source: {
      id: '00000000-0000-4000-8000-000000000004',
      label: 'Демонстрационный план',
      url: null, documentId: null, asOf: '2024-12-01',
    },
    supersedesEventId: null,
  }], '2026-01-01');
  expect(state.status).toBe('UNKNOWN');
  expect(state.eventId).toBeNull();
});
```
