# F10. Регистрация обращений и задачи исполнителей

**Цель:** Обращение надёжно регистрируется; задача обрабатывается отдельно; каждый заявитель сохраняет собственный ответ.
**Архитектура:** модуль существующего монорепозитория по contracts v1; разделённые production adapters и fixtures.
**Стек:** общий стек из 00-common.md; новые зависимости согласуются с интегратором.
**Приоритет:** P0
**Исполнитель:** Backend обращений

## Готовый промпт для агента

Ты реализуешь фичу F10 «Регистрация обращений и задачи исполнителей» портала строительства Тульской области.
Прочитай docs/agent-prompts/00-common.md, docs/agent-prompts/01-contracts.md и этот файл полностью. Если пакет приложен отдельно, используй эти документы из его корня. Не проси пользователя повторять сведения из них.

Ты не один в репозитории: сохраняй чужие изменения, соблюдай границы файлов. Общие DTO, корневые конфиги и lockfile изменяет интегратор. Внешний доступ не подменяй фиктивным успешным ответом.

## MVP — реализовать сейчас

1. Создать applicants, appeals, appeal_messages, tasks, appeal_task_links_history, task_comments и notification_outbox. Номер обращения генерирует БД; unique idempotency key связан с draftId/version.
2. Реализовать register: проверить описание 10–4000 символов после trim, категорию справочника, хотя бы одно READY photo, место (адрес или координаты) и время проблемы. Числа — стартовые конфигурационные лимиты; UI сообщает конкретную ошибку.
3. В транзакции зарегистрировать обращение, создать audit и outbox REGISTRATION. Повтор того же ключа возвращает прежний Appeal; тот же ключ с другим содержимым возвращает 409 IDEMPOTENCY_CONFLICT.
4. Добавить создание задачи, ответственного, срок, приоритет, комментарии и историю. Для MVP одна активная задача на обращение; разные обращения связываются с общей Task.
5. Реализовать переходы из 01-contracts.md, проверку Actor и If-Match. Переход ON_REVIEW требует текст результата и READY private фото; DONE подтверждает оператор. LLM не вызывает эти команды.
6. Внутренние комментарии отделить от текста заявителю. Reply API создаёт CLARIFICATION/ANSWER и outbox, принимает client idempotency key. Явное действие оператора отправляет ответ; сохранение внутреннего комментария ничего не отправляет.
7. Не менять все обращения на ANSWERED при DONE. Для каждого подготовить самостоятельный ответ и отдельное состояние отправки; текст может быть общий, адресат и записи разные.
8. Сохранить retry metadata и статус UNKNOWN для исходящих. Worker F12 читает outbox через lease/claim; потеря Redis не удаляет ожидающие уведомления.
9. Объект архивирован или отсутствует — существующее обращение всё равно открывается по сохранённой ссылке/снимку. Контакты видит только уполномоченная роль.

## Проверяемые сценарии MVP

1. Два одновременных register одного draft/version → один номер и одна логическая outbox запись.
2. Rollback регистрации → нет ни обращения, ни подтверждения.
3. Два заявителя одной проблемы → два обращения, одна связанная Task.
4. DONE → обращения не становятся ANSWERED без отдельного принятого ответа.
5. Чужой EXECUTOR не переводит статус и не скачивает фото; operator override требует reason.

Для бизнес-логики сначала реализуй перечисленные сценарии как падающие тесты, проверь ожидаемую причину падения, затем добавь реализацию. Для UI проверь действия через браузер и сохрани доказательство поведения. Контракт API проверяется общими schemas.


## TARGET — отдельное задание после приёмки MVP

Исполнять только если выбран режим TARGET. Сначала сохранить совместимость и данные принятой предыдущей версии.

1. Добавить календарь контрольных сроков, приостановку и возобновление по правилам ведомства; срок не выводить из придуманного нормативного периода.
2. Добавить делегирование, массовые операции с preview и историю отмены связи.
3. Если подтверждена потребность, поддержать несколько задач на обращение с отдельными результатами; это versioned изменение контракта, не скрытая смена семантики taskId.

Приёмка TARGET: перечисленные целевые поведения работают на согласованных данных и доступах, сценарии предыдущих версий проходят, миграции проверены на непустой БД. Если внешний источник недоступен, локальный adapter может быть готов, а внешняя приёмка остаётся открытой.

## Проверки и передача

Запусти после реализации соответствующие изменениям команды из 00-common.md:
```bash
pnpm typecheck
pnpm contracts:check
pnpm test:unit -- --feature=F10
pnpm test:integration -- --feature=F10
pnpm test:e2e -- --feature=F10
pnpm build
```
Не запускай неподходящую категорию как формальность: в handoff объясни, какие из unit/integration/e2e применимы этой фиче и какие реально выполнены. При применимом тестовом наборе ноль сценариев — ошибка проверки.
Подготовь docs/handoffs/F10.md по 02-handoff.md: изменённые файлы, exports, точное подключение, env, миграции, проверки, известные ограничения и интеграционный сценарий.
**Критерий завершения:** Обращение надёжно регистрируется; задача обрабатывается отдельно; каждый заявитель сохраняет собственный ответ.
