# F11. Сохраняемый диалог бота и локальный симулятор

**Цель:** Полный диалог и регистрация проверяются без токена MAX; тот же движок используется реальным каналом.
**Архитектура:** модуль существующего монорепозитория по contracts v1; разделённые production adapters и fixtures.
**Стек:** общий стек из 00-common.md; новые зависимости согласуются с интегратором.
**Приоритет:** P0
**Исполнитель:** Бот / backend интеграций

## Готовый промпт для агента

Прочитай docs/agent-prompts/00-common.md, docs/agent-prompts/01-contracts.md и этот файл полностью. Если пакет приложен отдельно, используй эти документы из его корня. Не проси пользователя повторять сведения из них.
Режим по умолчанию — MVP. Выполни его до проверяемого результата. Если пользователь явно выбрал V2 или TARGET, сначала проверь принятую предыдущую реализацию и выполни только соответствующее приращение. Не переписывай готовый MVP.
Ты не один в репозитории: сохраняй чужие изменения, соблюдай границы файлов. Общие DTO, корневые конфиги и lockfile изменяет интегратор. Внешний доступ не подменяй фиктивным успешным ответом.

## Вход и зависимости

F00; AppealRegistration contract F10 и media contract F02. Разработка возможна до токена MAX.

**Условие интеграции:** MVP диалога принимается на simulator; реальная регистрация после F10, канал MAX после F12.

**Потребляет:** BotSession/BotInput/BotAdvance/advanceBot; object lookup; READY photo assets; AppealRegistration.

**Предоставляет:** Чистая state machine; persisted sessions и effects; защищённый simulator dev API; adapter-independent диалог.

## MVP — реализовать сейчас

1. Реализовать advanceBot(session,input) как чистую функцию: OBJECT→CATEGORY→DESCRIPTION→PHOTO→LOCATION→OCCURRED_AT→REVIEW. Для каждого шага перечислить допустимые inputs, errors и SEND/REGISTER effects в runtime union.
2. START с валидным контекстом показывает название объекта и подтверждение выбора; без него даёт поиск/выбор. Архивированный/несуществующий объект объясняется, допускается сообщение с objectId=null и уточнённым местом.
3. Описание обязательно; фото минимум одно и READY; место проблемы отдельное от объекта, предлагается явно подтвердить адрес объекта или указать другое. Время допускает день/интервал с точностью, не silently now.
4. Добавить Назад, Изменить поле, Отмена и Подтвердить. Назад не теряет введённые поля. Отмена закрывает draft; повторная кнопка старой версии не регистрирует новый.
5. На REVIEW показать объект, категорию, текст, число фото, место и время. REGISTER effect появляется только по подтверждению актуальной версии после серверной валидации.
6. Сохранять session/version и effects атомарно; сериализовать входы одной сессии. Повторный BotInput.key не исполняет эффект второй раз. После рестарта продвинуть незавершённые эффекты.
7. Simulator позволяет подать текст, test photo и callback, видеть сообщения и переходы. Он доступен только в development или защищённом demo и явно помечен «Симулятор MAX».
8. Эффект REGISTER вызывает F10 с ключом draft/version; подтверждённый результат хранится, бот не создаёт второй Appeal при повторе.

## Проверяемые сценарии MVP

1. Пустое описание или отсутствие фото блокируют REVIEW/confirm с подсказкой.
2. Назад/редактирование сохраняют остальные данные; старый confirm callback отклоняется.
3. Перезапуск между сохранением и REGISTER effect → одно обращение после retry.
4. Два быстрых сообщения одного пользователя обрабатываются последовательно.
5. START без payload, битый payload и отсутствующий объект не ломают диалог.

Для бизнес-логики сначала реализуй перечисленные сценарии как падающие тесты, проверь ожидаемую причину падения, затем добавь реализацию. Для UI проверь действия через браузер и сохрани доказательство поведения. Контракт API проверяется общими schemas.


## TARGET — отдельное задание после приёмки MVP

Исполнять только если выбран режим TARGET. Сначала сохранить совместимость и данные принятой предыдущей версии.

1. Добавить несколько черновиков пользователя с явным выбором активного, срок хранения и возобновление.
2. Подключить последующие уточнения к конкретному Appeal по подписанному callback context; не относить ответ автоматически к последней задаче.
3. Добавить доступный текстовый путь, когда геолокация недоступна, и конфигурируемые категории по компетенции ведомства.

Приёмка TARGET: перечисленные целевые поведения работают на согласованных данных и доступах, сценарии предыдущих версий проходят, миграции проверены на непустой БД. Если внешний источник недоступен, локальный adapter может быть готов, а внешняя приёмка остаётся открытой.

## Проверки и передача

Запусти после реализации соответствующие изменениям команды из 00-common.md:
```bash
pnpm typecheck
pnpm contracts:check
pnpm test:unit -- --feature=F11
pnpm test:integration -- --feature=F11
pnpm test:e2e -- --feature=F11
pnpm build
```
Не запускай неподходящую категорию как формальность: в handoff объясни, какие из unit/integration/e2e применимы этой фиче и какие реально выполнены. При применимом тестовом наборе ноль сценариев — ошибка проверки.
Подготовь docs/handoffs/F11.md по 02-handoff.md: изменённые файлы, exports, точное подключение, env, миграции, проверки, известные ограничения и интеграционный сценарий.
**Критерий завершения:** Полный диалог и регистрация проверяются без токена MAX; тот же движок используется реальным каналом.
