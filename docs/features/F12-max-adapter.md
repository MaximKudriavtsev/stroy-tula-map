# F12. MAX: входящие события, файлы и уведомления

**Цель:** Обращения реально проходят через MAX и получают ответы; сохранены доказательства живой проверки или явно отмечены недостающие доступы.
**Архитектура:** модуль существующего монорепозитория по contracts v1; разделённые production adapters и fixtures.
**Стек:** общий стек из 00-common.md; новые зависимости согласуются с интегратором.
**Приоритет:** P0, внешний доступ обязателен для полной приёмки
**Исполнитель:** Интеграции

## Готовый промпт для агента

Ты реализуешь фичу F12 «MAX: входящие события, файлы и уведомления» портала строительства Тульской области.
Прочитай docs/agent-prompts/00-common.md, docs/agent-prompts/01-contracts.md и этот файл полностью. Если пакет приложен отдельно, используй эти документы из его корня. Не проси пользователя повторять сведения из них.
Режим по умолчанию — MVP. Выполни его до проверяемого результата. Если пользователь явно выбрал V2 или TARGET, сначала проверь принятую предыдущую реализацию и выполни только соответствующее приращение. Не переписывай готовый MVP.
Ты не один в репозитории: сохраняй чужие изменения, соблюдай границы файлов. Общие DTO, корневые конфиги и lockfile изменяет интегратор. Внешний доступ не подменяй фиктивным успешным ответом.

## Вход и зависимости

F00; F11 engine; F10 register/outbox; F02 media; botName/token и публичный HTTPS endpoint для live.

**Условие интеграции:** Webhook тестировать на sandbox/demo пользователях; успешный simulator не закрывает real MAX acceptance.

**Потребляет:** MessengerAdapter, BotInput, NotificationRequest, bot core и PostgreSQL outbox.

**Предоставляет:** Реальный MAX adapter, webhook inbox, медиа-ввод, deep link context, состояния исходящих и интеграционный журнал.

## MVP — реализовать сейчас

1. Перед кодированием проверить официальную документацию MAX для base URL, формата Authorization, событий, payload, файлов и webhook. Не копировать устаревший base URL из памяти. Сохранить дату проверки и ссылки в handoff.
2. Настроить token и webhook secret только в server env. Webhook проверяет secret, schema и ограничение тела; durable inbox commit предшествует 200. Обработчик не ждёт LLM и исходящие сообщения.
3. Преобразовать bot_started/message/callback/geolocation/photo события в BotInput. Выбрать dedupe key по документированному ID конкретного типа. При отсутствии общего update_id не выдумывать его.
4. Deep link передаёт object context в start payload до документированного лимита; без ПДн. Подписанный context либо непрозрачный ключ проверяется сервером; пользователь видит выбранный объект.
5. Полученные фото сохранить через F02 до confirm. Загрузка допускается только с документированного доверенного источника MAX; отклонять неожиданные URL/redirect и превышение размера. Не хранить лишь временный provider URL.
6. Worker сериализует session inputs и выполняет bot effects. Дубликаты webhook/confirm не создают вторую регистрацию; проверить реальные типы входа на тестовом боте.
7. Outbox sender учитывает rate limits и Retry-After, retry с backoff/jitter для явно повторяемых ошибок, PERMANENT_FAILURE для необратимых. После неопределённого сетевого исхода фиксирует UNKNOWN и политику безопасного ручного повтора.
8. API acceptance записывает providerMessageId, время, статус и перевод соответствующего ответа в ANSWERED. Не писать «прочитано» без такого события. Журнал показывает ошибку и возможность retry по роли.
9. Проверить вход, уточнение и ответ на двух тестовых аккаунтах. Если токена/домена нет, закончить adapter/tests на записанных обезличенных fixtures и перечислить оставшиеся live проверки.

## Проверяемые сценарии MVP

1. Неверный secret → отказ без durable бизнес-события.
2. Webhook duplicate и повтор confirm → один Appeal.
3. HTTP 200 возвращается после inbox commit; ошибка БД не маскируется успешным ответом.
4. Сбой отправки/429/timeout имеют разные состояния; Redis restart не теряет PostgreSQL outbox.
5. Живой тест: переход из карточки → фото → номер → уточнение → ответ в том же пользовательском чате.

Для бизнес-логики сначала реализуй перечисленные сценарии как падающие тесты, проверь ожидаемую причину падения, затем добавь реализацию. Для UI проверь действия через браузер и сохрани доказательство поведения. Контракт API проверяется общими schemas.


## TARGET — отдельное задание после приёмки MVP

Исполнять только если выбран режим TARGET. Сначала сохранить совместимость и данные принятой предыдущей версии.

1. Добавить мониторинг активности подписки webhook и процедуры восстановления, документированные лимиты и оповещения о накоплении очереди.
2. Реализовать ограниченную reconciliation с provider API, если она документированно доступна, для UNKNOWN outcomes.
3. Добавить контрактные тесты на изменения MAX и ротацию credentials без потери inbox/outbox.

Приёмка TARGET: перечисленные целевые поведения работают на согласованных данных и доступах, сценарии предыдущих версий проходят, миграции проверены на непустой БД. Если внешний источник недоступен, локальный adapter может быть готов, а внешняя приёмка остаётся открытой.

## Проверки и передача

Запусти после реализации соответствующие изменениям команды из 00-common.md:
```bash
pnpm typecheck
pnpm contracts:check
pnpm test:unit -- --feature=F12
pnpm test:integration -- --feature=F12
pnpm test:e2e -- --feature=F12
pnpm build
```
Не запускай неподходящую категорию как формальность: в handoff объясни, какие из unit/integration/e2e применимы этой фиче и какие реально выполнены. При применимом тестовом наборе ноль сценариев — ошибка проверки.
Подготовь docs/handoffs/F12.md по 02-handoff.md: изменённые файлы, exports, точное подключение, env, миграции, проверки, известные ограничения и интеграционный сценарий.
**Критерий завершения:** Обращения реально проходят через MAX и получают ответы; сохранены доказательства живой проверки или явно отмечены недостающие доступы.
