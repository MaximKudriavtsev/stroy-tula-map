# F13. Рабочее место оператора и исполнителя

**Цель:** Сотрудники завершают полный цикл без прямого редактирования БД и различают внутреннюю работу и сообщения жителю.
**Архитектура:** модуль существующего монорепозитория по contracts v1; разделённые production adapters и fixtures.
**Стек:** общий стек из 00-common.md; новые зависимости согласуются с интегратором.
**Приоритет:** P0
**Исполнитель:** Frontend админки

## MVP — реализовать сейчас

1. Очередь обращений: номер, объект/место, категория, дата, статус, task link; фильтры и пагинация. Отдельно очередь задач с исполнителем, сроком и приоритетом.
2. Карточка обращения показывает описание, безопасные private фото, source timestamps, историю, сообщения жителя и оператора. Скрыть контакты от исполнителя.
3. Создать/выбрать задачу и связать обращение через явное действие оператора. Показывать все связанные номера; исходные материалы остаются у обращений.
4. Реализовать назначение, срок, переходы, внутренние комментарии и результат с фото. Доступные переходы определяет сервер; 409 сохраняет локальный текст и предлагает перечитать состояние.
5. Кнопки «Внутренний комментарий», «Запросить уточнение», «Подготовить ответ», «Отправить в MAX» различаются. Подтверждение отправки показывает адресатов и текст; ответ каждому логируется отдельно.
6. Показывать QUEUED/ACCEPTED/FAILED/UNKNOWN для уведомления с понятными словами. Повторная отправка — по разрешению и с предупреждением о возможном дубле только для UNKNOWN.
7. Добавить пустые состояния для недоступного LLM, отсутствующего MAX и незагруженных файлов. Сбой аналитики не закрывает действия оператора.
8. Свежесть очереди через умеренный polling и ручное обновление в MVP; не терять введённый ответ при обновлении карточки.

## Проверяемые сценарии MVP

1. Два обращения → одна задача → результат → отдельные ответы обоим заявителям.
2. Комментарий не создаёт исходящее сообщение; явная отправка создаёт.
3. Executor не видит запрещённые контакты и действия.
4. Сетевая ошибка/409 не стирает введённый текст.
5. FAILED/UNKNOWN видны и не изображаются успешной доставкой.

Для бизнес-логики сначала реализуй перечисленные сценарии как падающие тесты, проверь ожидаемую причину падения, затем добавь реализацию. Для UI проверь действия через браузер и сохрани доказательство поведения. Контракт API проверяется общими schemas.


## TARGET — отдельное задание после приёмки MVP

Исполнять только если выбран режим TARGET. Сначала сохранить совместимость и данные принятой предыдущей версии.

1. Добавить SSE для обновлений с reconnect и cursor; конфликт совместного редактирования остаётся контролируемым.
2. Добавить сохранённые фильтры, массовое назначение и массовые ответы с preview адресатов.
3. Добавить визуальный SLA-календарь по серверным правилам и историю согласований ответа.

Приёмка TARGET: перечисленные целевые поведения работают на согласованных данных и доступах, сценарии предыдущих версий проходят, миграции проверены на непустой БД. Если внешний источник недоступен, локальный adapter может быть готов, а внешняя приёмка остаётся открытой.
