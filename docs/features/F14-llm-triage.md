# F14. Предварительный разбор LLM с проверкой сотрудником

**Цель:** Оператор получает проверяемые рекомендации; недоступность или ошибка модели не блокирует обработку.
**Архитектура:** модуль существующего монорепозитория по contracts v1; разделённые production adapters и fixtures.
**Стек:** общий стек из 00-common.md; новые зависимости согласуются с интегратором.
**Приоритет:** P1
**Исполнитель:** LLM / backend

## Готовый промпт для агента

Ты реализуешь фичу F14 «Предварительный разбор LLM с проверкой сотрудником» портала строительства Тульской области.
Прочитай docs/agent-prompts/00-common.md, docs/agent-prompts/01-contracts.md и этот файл полностью. Если пакет приложен отдельно, используй эти документы из его корня. Не проси пользователя повторять сведения из них.
Режим по умолчанию — MVP. Выполни его до проверяемого результата. Если пользователь явно выбрал V2 или TARGET, сначала проверь принятую предыдущую реализацию и выполни только соответствующее приращение. Не переписывай готовый MVP.
Ты не один в репозитории: сохраняй чужие изменения, соблюдай границы файлов. Общие DTO, корневые конфиги и lockfile изменяет интегратор. Внешний доступ не подменяй фиктивным успешным ответом.

## Вход и зависимости

F00, F10; candidates contract F15. Реальные похожие кандидаты не обязательны для первого анализа.

## MVP — реализовать сейчас

1. Выделить AnalysisProvider и конфигурацию OFF|FIXTURE|LIVE. FIXTURE явно помечается тестовым разбором; без доступа не выдавать шаблон за результат реальной модели.
2. Создать job после commit Appeal. Уникальность по версии обращения/правил/модели, ограниченные timeout/retries. Ошибка анализа не откатывает регистрацию и не меняет AppealStatus.
3. Сформировать prompt из утверждённых правил и текста как недоверенных данных. В MVP анализировать текст; фото модели не отправлять. Контакты, MAX identifiers и токены удалить.
4. Запросить JSON по AnalysisResult; runtime-валидация enum, длины текста, кандидатов и quote. invented candidate ID и категория вне справочника — invalid result с повтором либо FAILED.
5. Сохранить обоснование, source input version, rulesVersion, modelVersion и время. Новая версия обращения помечает прежний анализ устаревшим, но не стирает ручное решение.
6. Панель показывает компетенцию, spam flag, недостающую информацию, срочность и сводку. Оператор принимает/исправляет каждую рекомендацию и оставляет причину.
7. Для OUT_OF_SCOPE/SPAM не выполнять автоматический отказ/удаление. Рекомендация срочности не отправляет автоматически ответ или команду task transition.

## Проверяемые сценарии MVP

1. Provider timeout → Appeal остаётся REGISTERED, analysis FAILED.
2. Prompt injection в тексте не получает инструменты и не меняет правила workflow.
3. Ответ с неизвестным ID/категорией отклонён.
4. Два одинаковых анализа версии не плодят results; новая версия сохраняет предыдущую.
5. Ручной review сохраняется и не перезаписывается job завершившимся позже.

Для бизнес-логики сначала реализуй перечисленные сценарии как падающие тесты, проверь ожидаемую причину падения, затем добавь реализацию. Для UI проверь действия через браузер и сохрани доказательство поведения. Контракт API проверяется общими schemas.

## V2 — отдельное задание после приёмки MVP

Исполнять только если выбран режим V2. Вход — принятый MVP этой фичи; внешние зависимости перечислены в шагах.

1. Добавить реального согласованного провайдера, если MVP был на fixtures, и evaluation corpus из обезличенных кейсов с ожидаемыми категориями/компетенцией.
2. Добавить retrieval только утверждённых правил ведомства с ссылками и версиями; trace показывает использованные фрагменты.
3. Подключить shortlist F15 и предложения task link. Решение связывания остаётся явным действием оператора.

Приёмка V2: все сценарии MVP проходят; для каждого нового поведения добавлена проверка успешного пути и указанного отказа.

## TARGET — отдельное задание после приёмки V2

Исполнять только если выбран режим TARGET. Сначала сохранить совместимость и данные принятой предыдущей версии.

1. Добавить сравнение моделей на фиксированном корпусе, метрики ложной срочности/неверной компетенции, стоимость и задержку; выпуск новой версии правил через review.
2. При согласованной обработке добавить отдельный visual-analysis adapter с минимальными данными и resource budget.
3. Настроить data retention и контролируемый доступ к обезличенным traces; не сохранять произвольные скрытые рассуждения модели, только предусмотренное обоснование.

Приёмка TARGET: перечисленные целевые поведения работают на согласованных данных и доступах, сценарии предыдущих версий проходят, миграции проверены на непустой БД. Если внешний источник недоступен, локальный adapter может быть готов, а внешняя приёмка остаётся открытой.

## Проверки и передача

Запусти после реализации соответствующие изменениям команды из 00-common.md:
```bash
pnpm typecheck
pnpm contracts:check
pnpm test:unit -- --feature=F14
pnpm test:integration -- --feature=F14
pnpm test:e2e -- --feature=F14
pnpm build
```
Не запускай неподходящую категорию как формальность: в handoff объясни, какие из unit/integration/e2e применимы этой фиче и какие реально выполнены. При применимом тестовом наборе ноль сценариев — ошибка проверки.
Подготовь docs/handoffs/F14.md по 02-handoff.md: изменённые файлы, exports, точное подключение, env, миграции, проверки, известные ограничения и интеграционный сценарий.
**Критерий завершения:** Оператор получает проверяемые рекомендации; недоступность или ошибка модели не блокирует обработку.
