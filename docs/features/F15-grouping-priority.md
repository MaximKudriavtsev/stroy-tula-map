# F15. Похожие обращения, объединение и объяснимый приоритет

**Цель:** Сотрудник быстро находит связанную проблему и понимает приоритет, сохраняя контроль объединения.
**Архитектура:** модуль существующего монорепозитория по contracts v1; разделённые production adapters и fixtures.
**Стек:** общий стек из 00-common.md; новые зависимости согласуются с интегратором.
**Приоритет:** P1
**Исполнитель:** Backend аналитики обращений

## Готовый промпт для агента

Ты реализуешь фичу F15 «Похожие обращения, объединение и объяснимый приоритет» портала строительства Тульской области.
Прочитай docs/agent-prompts/00-common.md, docs/agent-prompts/01-contracts.md и этот файл полностью. Если пакет приложен отдельно, используй эти документы из его корня. Не проси пользователя повторять сведения из них.
Режим по умолчанию — MVP. Выполни его до проверяемого результата. Если пользователь явно выбрал V2 или TARGET, сначала проверь принятую предыдущую реализацию и выполни только соответствующее приращение. Не переписывай готовый MVP.
Ты не один в репозитории: сохраняй чужие изменения, соблюдай границы файлов. Общие DTO, корневые конфиги и lockfile изменяет интегратор. Внешний доступ не подменяй фиктивным успешным ответом.

## Вход и зависимости

F00, F10; F13 для UI; F14 необязателен в MVP.

**Условие интеграции:** F14 получает shortlist IDs; F10 сохраняет основную связь Appeal→Task.

**Потребляет:** Appeals/tasks, география, категории, время, unique applicant accounts; operator permissions.

**Предоставляет:** Candidates API, priority explanation, ручное link/merge с audit и история overrides.

## MVP — реализовать сейчас

1. Построить детерминированный shortlist: одинаковый objectId либо близость в метрах при наличии проверенных координат; затем категория, временное окно и PostgreSQL text similarity. Базовые окно 30 дней/радиус 200 м — конфигурация, не доказательство одинаковой проблемы.
2. Вернуть кандидатов с причинами: совпал объект, расстояние, категория, близкий текст. Отсутствие координат не заменять точкой [0,0]. Не склеивать обращения автоматически.
3. Приоритет MVP задаёт оператор LOW/NORMAL/HIGH/URGENT. Рядом показывать факторы: потенциальная опасность, число уникальных MAX accounts, новые сообщения за 24ч против предыдущих 24ч, просрочка, повторное открытие.
4. Дубли одного аккаунта не увеличивают счётчик заявителей. Не называть эти аккаунты доказанно независимыми людьми. Уникальность определяется внутри одной подтверждённой группы проблемы.
5. Создать link и controlled merge: выбрать основную задачу, показать связанные обращения, ответственного/срок/приоритет, решить конфликты явно. Сохранять source Task с mergedIntoTaskId и историей; это не дополнительный TaskStatus. Не удалять материалы.
6. Merge проверяет scope всех затронутых задач, блокирует concurrent updates и циклы, сохраняет idempotency. DONE задача с новым событием не открывается автоматически: оператор подтверждает повторное возникновение.
7. Подготовить интерфейс PriorityPolicy.evaluate(features) с объяснениями без обязательного автоматического score в MVP.

## Проверяемые сценарии MVP

1. Десять дублей одного пользователя → один unique applicant factor.
2. Две похожие формулировки разных объектов не объединяются автоматически.
3. Merge сохраняет номера/ответы/историю, второй повтор не дублирует links.
4. Цикл merge или задача вне scope отклоняется.
5. Старые/нулевые временные окна не дают division by zero или бесконечный рост.

Для бизнес-логики сначала реализуй перечисленные сценарии как падающие тесты, проверь ожидаемую причину падения, затем добавь реализацию. Для UI проверь действия через браузер и сохрани доказательство поведения. Контракт API проверяется общими schemas.

## V2 — отдельное задание после приёмки MVP

Исполнять только если выбран режим V2. Вход — принятый MVP этой фичи; внешние зависимости перечислены в шагах.

1. Добавить версионированный rules score после утверждения коэффициентов. До утверждения включать только DEMO policy. Пример demo score: danger flag +50, unique accounts min(n,5)*5, count growth +10, overdue +15, reopened +20; пороги ≤24 LOW, 25–49 NORMAL, 50–74 HIGH, ≥75 URGENT. Подпись «Демонстрационная методика».
2. Подтверждённая сотрудником непосредственная опасность даёт URGENT независимо от популярности; LLM-only danger остаётся сигналом для проверки.
3. Показывать вклад каждого фактора и policyVersion, сохранять ручной override с причиной до явной отмены.

Приёмка V2: все сценарии MVP проходят; для каждого нового поведения добавлена проверка успешного пути и указанного отказа.

## TARGET — отдельное задание после приёмки V2

Исполнять только если выбран режим TARGET. Сначала сохранить совместимость и данные принятой предыдущей версии.

1. Добавить embeddings и reranking поверх географического/category shortlist, оценить precision/recall на размеченных парах.
2. Проверить защиту метрик от массовых повторов и повторной регистрации; не собирать лишние идентификаторы.
3. Поддержать split ошибочно объединённой группы с сохранением истории и повторной оценкой задач.

Приёмка TARGET: перечисленные целевые поведения работают на согласованных данных и доступах, сценарии предыдущих версий проходят, миграции проверены на непустой БД. Если внешний источник недоступен, локальный adapter может быть готов, а внешняя приёмка остаётся открытой.

## Проверки и передача

Запусти после реализации соответствующие изменениям команды из 00-common.md:
```bash
pnpm typecheck
pnpm contracts:check
pnpm test:unit -- --feature=F15
pnpm test:integration -- --feature=F15
pnpm test:e2e -- --feature=F15
pnpm build
```
Не запускай неподходящую категорию как формальность: в handoff объясни, какие из unit/integration/e2e применимы этой фиче и какие реально выполнены. При применимом тестовом наборе ноль сценариев — ошибка проверки.
Подготовь docs/handoffs/F15.md по 02-handoff.md: изменённые файлы, exports, точное подключение, env, миграции, проверки, известные ограничения и интеграционный сценарий.
**Критерий завершения:** Сотрудник быстро находит связанную проблему и понимает приоритет, сохраняя контроль объединения.
