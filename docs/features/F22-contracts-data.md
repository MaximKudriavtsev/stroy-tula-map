# F22. Сведения о строительных контрактах

**Цель:** Житель видит проверяемые сведения о контрактах, а отсутствие доступа не изображается готовой интеграцией.
**Архитектура:** модуль существующего монорепозитория по contracts v1; разделённые production adapters и fixtures.
**Стек:** общий стек из 00-common.md; новые зависимости согласуются с интегратором.
**Приоритет:** P2 или обязательная функция по критериям
**Исполнитель:** Интеграции данных

## Готовый промпт для агента

Ты реализуешь фичу F22 «Сведения о строительных контрактах» портала строительства Тульской области.
Прочитай docs/agent-prompts/00-common.md, docs/agent-prompts/01-contracts.md и этот файл полностью. Если пакет приложен отдельно, используй эти документы из его корня. Не проси пользователя повторять сведения из них.
Режим по умолчанию — MVP. Выполни его до проверяемого результата. Если пользователь явно выбрал V2 или TARGET, сначала проверь принятую предыдущую реализацию и выполни только соответствующее приращение. Не переписывай готовый MVP.
Ты не один в репозитории: сохраняй чужие изменения, соблюдай границы файлов. Общие DTO, корневые конфиги и lockfile изменяет интегратор. Внешний доступ не подменяй фиктивным успешным ответом.

## Вход и зависимости

F00, F03/F06, реальные номера/ссылки контрактов для наполнения.

**Условие интеграции:** Совпадение подрядчика/названия само по себе не создаёт связь с контрактом.

**Потребляет:** Object/project IDs, внешняя система, contract identifier, public source.

**Предоставляет:** Ручные подтверждённые ссылки контрактов и read API с metadata.

## MVP — реализовать сейчас

1. Создать contract reference: system, externalId, publicUrl, object/project links, source/asOf, verifiedBy. Поддержать несколько контрактов объекта и один контракт нескольких объектов.
2. Редактор вручную добавляет номер и подтверждённую ссылку, проверяет связь с объектом. Отсутствие номера отображается «Сведения о контракте не добавлены».
3. В MVP не извлекать автоматически стоимость/сроки из произвольной HTML-страницы. При ручном вводе суммы хранить currency, источник и дату, не выводить сумму из мощности.
4. Публичная карточка содержит номер, источник и подтверждённые реквизиты. Ссылки валидируются по разрешённым схемам и доменам, не запускают произвольные server-side запросы.
5. Обновления проходят draft→publish вместе с объектом. Админка фиксирует автора подтверждения связи.

## Проверяемые сценарии MVP

1. Один контракт связан с двумя объектами без удвоения в проектном списке.
2. Неподтверждённая draft ссылка отсутствует публично.
3. Некорректный URL/ID отклонён, неизвестная сумма не равна 0.

Для бизнес-логики сначала реализуй перечисленные сценарии как падающие тесты, проверь ожидаемую причину падения, затем добавь реализацию. Для UI проверь действия через браузер и сохрани доказательство поведения. Контракт API проверяется общими schemas.


## TARGET — отдельное задание после приёмки MVP

Исполнять только если выбран режим TARGET. Сначала сохранить совместимость и данные принятой предыдущей версии.

1. Подключить документированный официальный API/выгрузку с разрешённым доступом, версией данных и retry.
2. Сопоставлять по внешнему идентификатору и ручному решению; сохранять conflicts при расхождении сведений.
3. Добавить изменения суммы/сроков и статуса как датированную историю, отдельно от строительной готовности объекта.

Приёмка TARGET: перечисленные целевые поведения работают на согласованных данных и доступах, сценарии предыдущих версий проходят, миграции проверены на непустой БД. Если внешний источник недоступен, локальный adapter может быть готов, а внешняя приёмка остаётся открытой.

## Проверки и передача

Запусти после реализации соответствующие изменениям команды из 00-common.md:
```bash
pnpm typecheck
pnpm contracts:check
pnpm test:unit -- --feature=F22
pnpm test:integration -- --feature=F22
pnpm test:e2e -- --feature=F22
pnpm build
```
Не запускай неподходящую категорию как формальность: в handoff объясни, какие из unit/integration/e2e применимы этой фиче и какие реально выполнены. При применимом тестовом наборе ноль сценариев — ошибка проверки.
Подготовь docs/handoffs/F22.md по 02-handoff.md: изменённые файлы, exports, точное подключение, env, миграции, проверки, известные ограничения и интеграционный сценарий.
**Критерий завершения:** Житель видит проверяемые сведения о контрактах, а отсутствие доступа не изображается готовой интеграцией.
