# F24. Интеграция с ПОС или внешней системой обращений

**Цель:** Локальная готовность и реальная интеграция имеют разные критерии; TARGET завершён только подтверждённым обменом с внешней системой.
**Архитектура:** модуль существующего монорепозитория по contracts v1; разделённые production adapters и fixtures.
**Стек:** общий стек из 00-common.md; новые зависимости согласуются с интегратором.
**Приоритет:** Отдельный объём после получения требований
**Исполнитель:** Интеграции ведомства

## Готовый промпт для агента

Ты реализуешь фичу F24 «Интеграция с ПОС или внешней системой обращений» портала строительства Тульской области.
Прочитай docs/agent-prompts/00-common.md, docs/agent-prompts/01-contracts.md и этот файл полностью. Если пакет приложен отдельно, используй эти документы из его корня. Не проси пользователя повторять сведения из них.
Режим по умолчанию — MVP. Выполни его до проверяемого результата. Если пользователь явно выбрал V2 или TARGET, сначала проверь принятую предыдущую реализацию и выполни только соответствующее приращение. Не переписывай готовый MVP.
Ты не один в репозитории: сохраняй чужие изменения, соблюдай границы файлов. Общие DTO, корневые конфиги и lockfile изменяет интегратор. Внешний доступ не подменяй фиктивным успешным ответом.

## Вход и зависимости

F00, F10; документация, credentials, sandbox, правила маршрутизации и регламент.

**Условие интеграции:** Собственная админка и MAX не считаются интеграцией с ПОС.

**Потребляет:** Appeal/Task, внешняя контрактная спецификация при наличии; local/external IDs.

**Предоставляет:** ExternalCaseLink, POS adapter port, statuses и журнал; реальный transport только по документации.

## MVP — реализовать сейчас

1. Создать port внешней системы и запись связи localAppealId/externalSystem/externalId/syncState/lastSyncAt. Не выдумывать endpoint или поля ПОС.
2. Без sandbox/documentation реализовать выключенный adapter и тестовый transport, отмеченный SIMULATED. Дать локальный JSON export по документированной внутренней схеме, если нужен обмен для обсуждения.
3. Сохранять local number отдельно от externalId. В UI показывать «Не передано во внешнюю систему», пока нет подтверждённого результата.
4. Описать mapping draft: какие сведения необходимо передать, какие поля содержат персональные данные, кто подтверждает передачу. Реальное правило определяется заказчиком, не моделью.
5. Подготовить contract tests адаптера на synthetic fixtures и журнал состояний. Не объявлять доставку/регистрацию внешней системы при mock response.

## Проверяемые сценарии MVP

1. Локальный номер не подставляется вместо externalId.
2. Выключенный adapter не делает внешних запросов и сообщает корректный статус.
3. Повтор synthetic export не создаёт две external links.

Для бизнес-логики сначала реализуй перечисленные сценарии как падающие тесты, проверь ожидаемую причину падения, затем добавь реализацию. Для UI проверь действия через браузер и сохрани доказательство поведения. Контракт API проверяется общими schemas.


## TARGET — отдельное задание после приёмки MVP

Исполнять только если выбран режим TARGET. Сначала сохранить совместимость и данные принятой предыдущей версии.

1. После получения официальной спецификации реализовать auth, retries/idempotency, export, attachments и входящие статусы через документированный transport.
2. Согласовать mapping workflow и источник истины: какие переходы управляются локально, какие внешней системой; циклическая синхронизация запрещена.
3. Провести sandbox round trip, подтверждение внешнего ID, уточнение и завершение; проверить rollback/replay и аудит передачи.
4. Получить разрешение эксплуатации и включить live только после приёмки владельцем интеграции.

Приёмка TARGET: перечисленные целевые поведения работают на согласованных данных и доступах, сценарии предыдущих версий проходят, миграции проверены на непустой БД. Если внешний источник недоступен, локальный adapter может быть готов, а внешняя приёмка остаётся открытой.

## Проверки и передача

Запусти после реализации соответствующие изменениям команды из 00-common.md:
```bash
pnpm typecheck
pnpm contracts:check
pnpm test:unit -- --feature=F24
pnpm test:integration -- --feature=F24
pnpm test:e2e -- --feature=F24
pnpm build
```
Не запускай неподходящую категорию как формальность: в handoff объясни, какие из unit/integration/e2e применимы этой фиче и какие реально выполнены. При применимом тестовом наборе ноль сценариев — ошибка проверки.
Подготовь docs/handoffs/F24.md по 02-handoff.md: изменённые файлы, exports, точное подключение, env, миграции, проверки, известные ограничения и интеграционный сценарий.
**Критерий завершения:** Локальная готовность и реальная интеграция имеют разные критерии; TARGET завершён только подтверждённым обменом с внешней системой.
