# F25. Подтверждение устранения жителем

**Цель:** Житель подтверждает или оспаривает устранение, а оператор видит обратную связь по каждому обращению.
**Архитектура:** модуль существующего монорепозитория по contracts v1; разделённые production adapters и fixtures.
**Стек:** общий стек из 00-common.md; новые зависимости согласуются с интегратором.
**Приоритет:** P2
**Исполнитель:** Бот / workflow

## Готовый промпт для агента

Ты реализуешь фичу F25 «Подтверждение устранения жителем» портала строительства Тульской области.
Прочитай docs/agent-prompts/00-common.md, docs/agent-prompts/01-contracts.md и этот файл полностью. Если пакет приложен отдельно, используй эти документы из его корня. Не проси пользователя повторять сведения из них.
Режим по умолчанию — MVP. Выполни его до проверяемого результата. Если пользователь явно выбрал V2 или TARGET, сначала проверь принятую предыдущую реализацию и выполни только соответствующее приращение. Не переписывай готовый MVP.
Ты не один в репозитории: сохраняй чужие изменения, соблюдай границы файлов. Общие DTO, корневые конфиги и lockfile изменяет интегратор. Внешний доступ не подменяй фиктивным успешным ответом.

## Вход и зависимости

F00, F10/F11/F12, принятый оператором результат задачи.

**Условие интеграции:** Оценка ответа не используется как удовлетворённость инфраструктурой в F16.

**Потребляет:** Appeal, подтверждённый ответ, заявитель MAX, подписанный callback context.

**Предоставляет:** ResidentConfirmation с answer YES/NO/UNSURE, временем и optional comment; операторская очередь повторной проверки.

## MVP — реализовать сейчас

1. После принятого API ответа предложить конкретному заявителю «Проблема устранена? Да / Нет / Не могу проверить». Связать callback с appealId, recipient и nonce/version.
2. Проверять принадлежность callback отправителю обращения, срок действия и повтор. Ответ одного пользователя не распространяется на остальные обращения той же задачи.
3. YES сохраняет подтверждение, NO предлагает описание/фото и создаёт рекомендацию повторной проверки оператору. Не переоткрывать и не закрывать Task автоматически.
4. Нет ответа не считается согласием. UNSURE не считается отрицательной оценкой.
5. В админке показать ответы по каждому Appeal и сигнал расхождения после DONE. Не включать оценку в инфраструктурную удовлетворённость.

## Проверяемые сценарии MVP

1. Чужой MAX user не отвечает по nonce другого заявителя.
2. Повтор callback идемпотентен.
3. Отсутствие ответа остаётся неизвестным.
4. NO сохраняет feedback и сигнал оператору, без автоматического task transition.

Для бизнес-логики сначала реализуй перечисленные сценарии как падающие тесты, проверь ожидаемую причину падения, затем добавь реализацию. Для UI проверь действия через браузер и сохрани доказательство поведения. Контракт API проверяется общими schemas.


## TARGET — отдельное задание после приёмки MVP

Исполнять только если выбран режим TARGET. Сначала сохранить совместимость и данные принятой предыдущей версии.

1. Добавить регулируемые напоминания с frequency cap и отказом от напоминаний.
2. Поддержать уточнения и повторную проверку с новым циклом nonce, сохраняя старые ответы.
3. Строить отдельную аналитику качества ответа с периодом и количеством ответов, без смешения с городскими survey.

Приёмка TARGET: перечисленные целевые поведения работают на согласованных данных и доступах, сценарии предыдущих версий проходят, миграции проверены на непустой БД. Если внешний источник недоступен, локальный adapter может быть готов, а внешняя приёмка остаётся открытой.

## Проверки и передача

Запусти после реализации соответствующие изменениям команды из 00-common.md:
```bash
pnpm typecheck
pnpm contracts:check
pnpm test:unit -- --feature=F25
pnpm test:integration -- --feature=F25
pnpm test:e2e -- --feature=F25

```
Не запускай неподходящую категорию как формальность: в handoff объясни, какие из unit/integration/e2e применимы этой фиче и какие реально выполнены. При применимом тестовом наборе ноль сценариев — ошибка проверки.
Подготовь docs/handoffs/F25.md по 02-handoff.md: изменённые файлы, exports, точное подключение, env, миграции, проверки, известные ограничения и интеграционный сценарий.
**Критерий завершения:** Житель подтверждает или оспаривает устранение, а оператор видит обратную связь по каждому обращению.
