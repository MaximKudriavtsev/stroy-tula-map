# F26. Сквозная интеграция, проверка и выпуск стенда

**Цель:** Команда получает воспроизводимый проверенный результат и знает, какие внешние части действительно готовы.
**Архитектура:** модуль существующего монорепозитория по contracts v1; разделённые production adapters и fixtures.
**Стек:** общий стек из 00-common.md; новые зависимости согласуются с интегратором.
**Приоритет:** Обязательный gate; повторяется после каждой волны
**Исполнитель:** Интегратор / QA / инфраструктура

## Готовый промпт для агента

Ты реализуешь фичу F26 «Сквозная интеграция, проверка и выпуск стенда» портала строительства Тульской области.
Прочитай docs/agent-prompts/00-common.md, docs/agent-prompts/01-contracts.md и этот файл полностью. Если пакет приложен отдельно, используй эти документы из его корня. Не проси пользователя повторять сведения из них.
Режим по умолчанию — MVP. Выполни его до проверяемого результата. Если пользователь явно выбрал V2 или TARGET, сначала проверь принятую предыдущую реализацию и выполни только соответствующее приращение. Не переписывай готовый MVP.
Ты не один в репозитории: сохраняй чужие изменения, соблюдай границы файлов. Общие DTO, корневые конфиги и lockfile изменяет интегратор. Внешний доступ не подменяй фиктивным успешным ответом.

## Вход и зависимости

Для P0: F00–F06 и F10–F13. Для demo: дополнительно выбранные F07–F09/F14/F15. P2 принимается по отдельному scope.

**Условие интеграции:** Не ждать все необязательные фичи. Принимать только явно выбранный набор, не считать mocks live интеграцией.

**Потребляет:** Feature handoffs, migrations, module exports, actual env/accesses, выбранный scope релиза.

**Предоставляет:** Интегрированный стенд, report проверок, runbook и сценарий защиты с честными ограничениями.

## MVP — реализовать сейчас

1. Зафиксировать release-scope по IDs/версиям. Принять dependency gates; зарегистрировать modules/routes/extensions, упорядочить миграции, регенерировать клиент и проверить contracts.
2. Развернуть demo окружение с PostgreSQL, Redis, storage, API, worker и двумя frontend. Разделить dev/demo secrets и данные от production; админка защищена, simulator только явно разрешён на demo.
3. Прогнать миграции на чистой БД и повторный запуск. Seed DEMO идемпотентен и не запускается автоматически в production.
4. Сценарий P0: редактор создаёт и публикует объект → житель находит карточку → MAX/simulator регистрирует сообщение с фото → оператор назначает задачу → исполнитель прикладывает результат → оператор отправляет ответ.
5. Сценарий demo: добавить generic модели F07, подтверждённые FACT/PLAN события F08, показатель F09, второе обращение и предложение F14/F15. Каждый demo data block помечен.
6. Проверить отказы: provider LLM down, MAX 429/timeout, Redis restart, worker crash после claim, API restart, storage unavailable, WebGL disabled. Регистрация не теряется после durable commit; очередь восстанавливается.
7. Проверить роли, private files, draft leaks, CSRF и отсутствие secrets в public bundle/logs. Проверить standalone anonymous public list и protected admin.
8. Записать performance baseline с устройством, браузером, сетью, data count, model budget. Начальные цели для согласованного стенда: usable список/карточка ≤3с на 10 Мбит/с и 100мс RTT; API list p95≤500мс при 20 concurrent users на test dataset; 3D ≥30 FPS на согласованном устройстве. Это цели приёмки, не уже полученные результаты.
9. Подготовить runbook: запуск, backup, проверка restore, миграции, ротация tokens, restart/retry, режимы mock/live, источники DEMO и список неподтверждённых интеграций. Публикацию во внешнюю среду выполнить только в рамках выбранного задания.

## Проверяемые сценарии MVP

1. E2E сквозного сценария на двух ролях и двух заявителях проходит.
2. Повтор регистрации/перезапуск не создаёт второй номер.
3. Snapshot опубликованного объекта консистентен во всех дочерних API.
4. Сценарии 390x844 и desktop проходят, без WebGL доступен список.
5. Restore восстанавливает записи и ссылки на файлы; ожидающие outbox не теряются.
6. Report явно разделяет реально проверенный MAX/LLM/POS и simulator.

Для бизнес-логики сначала реализуй перечисленные сценарии как падающие тесты, проверь ожидаемую причину падения, затем добавь реализацию. Для UI проверь действия через браузер и сохрани доказательство поведения. Контракт API проверяется общими schemas.


## TARGET — отдельное задание после приёмки MVP

Исполнять только если выбран режим TARGET. Сначала сохранить совместимость и данные принятой предыдущей версии.

1. Разделить production роли сервисов и доступ к данным, настроить HTTPS/reverse proxy, backups вне основной машины и мониторинг по согласованной эксплуатации.
2. Ввести staged rollout, smoke после deploy и совместимые migrations. Откат приложения не должен предполагать разрушительный откат БД.
3. Согласовать RPO/RTO и SLO с владельцем; подтвердить восстановление практическим упражнением, а не наличием cron backup.
4. Принять только выбранные P2 интеграции на реальных источниках и подготовить инструкцию сотрудникам.

Приёмка TARGET: перечисленные целевые поведения работают на согласованных данных и доступах, сценарии предыдущих версий проходят, миграции проверены на непустой БД. Если внешний источник недоступен, локальный adapter может быть готов, а внешняя приёмка остаётся открытой.

## Проверки и передача

Запусти после реализации соответствующие изменениям команды из 00-common.md:
```bash
pnpm typecheck
pnpm contracts:check
pnpm test:unit -- --feature=F26
pnpm test:integration -- --feature=F26
pnpm test:e2e -- --feature=F26
pnpm build
```
Не запускай неподходящую категорию как формальность: в handoff объясни, какие из unit/integration/e2e применимы этой фиче и какие реально выполнены. При применимом тестовом наборе ноль сценариев — ошибка проверки.
Подготовь docs/handoffs/F26.md по 02-handoff.md: изменённые файлы, exports, точное подключение, env, миграции, проверки, известные ограничения и интеграционный сценарий.
**Критерий завершения:** Команда получает воспроизводимый проверенный результат и знает, какие внешние части действительно готовы.
